For teams and leaders

Your agents need your company's rules in a form they can check.

SIGN is a way to write down your company's definitions, rules and relationships so the agents you run can check them, cite them and stay current with them. This page explains what changes, how to try it, and what it costs.

The problem

Rules pasted into prompts cause three problems.

Rules get copied into prompts

Each team pastes its own version of a policy into its own prompts. When the policy changes, nobody knows which copies are out of date.

Agents cannot tell a rule from a note

In a page of prose, a hard limit and a passing remark look the same. The agent has to guess which one it must obey.

Nobody can trace an answer

When an agent acts on a rule, there is often no record of which version it used or where that rule came from.

What SIGN changes

One written source, in a form agents can check.

TodayWith SIGN
A policy lives in a PDF and in a dozen prompts.The policy lives in one SIGN document. Agents read the current version from a compiled bundle, so you update the source, not every copy.
A limit is a sentence somewhere in the text.A limit is a typed constraint that names what it requires and what it forbids.
Retired guidance stays in circulation.Each document carries a status. The compiler leaves inactive and deprecated documents out of the bundle.
The source of a fact is unknown.Each fact is marked as asserted or inferred, with where it came from.
Long context is loaded on every call.Agents load a short index on every call and fetch full documents only when needed. In the specification's benchmark, one document took 379 tokens in SIGN against 978 in JSON.
How to adopt it

Start with one body of knowledge and one agent.

You can hand this plan to an engineer as written. Their side of each step is in the engineer guide.

  1. Step 1

    Pick something small that agents already use.

    A refund policy, a product glossary, an approval matrix, or one code repository. Choose something with a clear owner who can say whether the result is right.

  2. Step 2

    Convert it.

    Existing documents go through sign-ingest. A code repository goes through the sign-encode-repo skill in Claude Code. New knowledge with no document yet can be drafted with the sign-draft skill. All three are open and run on your own machines.

  3. Step 3

    Have the owner review it.

    Treat everything the tools generate as a draft. The owner reads each document, corrects it, and sets its status to active. The validator then checks structure, links and the index size.

  4. Step 4

    Give it to one agent.

    The engineer loads the index into that agent's prompt and adds a tool that fetches full documents by ID. Nothing about the model or framework has to change.

  5. Step 5

    Compare the results.

    Before you switch, record a baseline: run a handful of real tasks with your current prompts and note the tokens each call used. Then run the same tasks with the SIGN index. Check whether the agent applied the rule, whether it cited the document, and how the token counts compare. Then decide whether to add the next body of knowledge.

Questions teams ask

Cost, control and stability.

What does it cost?
The specification and the reference tools are free and open source under the Apache License 2.0. Your costs are the time to convert and review knowledge, and the model usage of the agents that read it.
Does it tie us to a model or vendor?
No. SIGN files are plain text in your own repository. Any model that reads text can read them, and the validator is a small Node.js program you can run anywhere.
Does it replace tools we already pay for?
SIGN is a file format and a set of open tools, not a platform. It does not require a license from any model or cloud vendor, so the knowledge you write in it stays usable whichever agents and tools you choose later. Whether that lets you drop or downgrade an existing tool depends on what that tool does for you today.
Does our code or knowledge leave our machines?
The validator and sign-ingest run locally. The sign-encode-repo skill states in its operating contract that it sends no repository content to a network endpoint and never edits source files. The model you run the Claude Code skills with is your choice and follows your existing terms with that provider.
Who maintains SIGN?
Five Deep maintains the specification and reference tools. SIGN began at Career Highways, and version 1.0 was published in April 2026. Changes are proposed and discussed in public issues on GitHub.
Is it stable enough to build on?
The specification is at version 1.0, and new sigils go through a proposal before they are added. The reference tools are at version 0.1, so expect them to change faster than the specification.
For your security team

A note you can send before anyone runs the tools.

Running a tool against a code repository usually needs a security review. Copy this note, add your own details, and send it with the links.

Note to your security team
We would like to try SIGN, an open specification (Apache 2.0) for writing
company rules and definitions in a form AI agents can read.

What we plan to run, all on our own machines:
- The SIGN validator: a Node.js program with no third-party dependencies.
  It reads .sign files and writes compiled files to a folder we choose.
- sign-ingest: converts documents we select into .sign files.
- The sign-encode-repo skill for Claude Code, on one repository. Its
  operating contract says it writes only to .agent/sign/ and one block in
  AGENTS.md and CLAUDE.md, never edits source code, sends no repository
  content to a network endpoint, and redacts secrets before it writes.

The skill runs inside Claude Code, so prompts go to the model provider we
already use, under our existing terms with that provider.

Source code and the operating contract are public:
https://github.com/sign-protocol/sign-lang
https://github.com/sign-protocol/sign-tools
Maintainer's trust information: https://trust.fivedeep.ai

Try the tools on a small or sample repository first. That lets your team check the output before anything runs on your main codebase.
